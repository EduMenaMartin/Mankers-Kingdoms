## The two-phase flow

GodotSteam separates **lobby management** (who's in the group, via Steam's servers) from **P2P transport** (the actual game networking, via `MultiplayerPeer`). You need both, in this order:

**Phase 1 — Lobby (Matchmaking class):** establishes "who is playing together" via Steam's own infrastructure.
**Phase 2 — Transport (MultiplayerPeer class):** once the lobby exists, wire up the actual Godot `MultiplayerAPI` peer so `Multiplayer.MultiplayerPeer` works as normal for RPCs, spawning, etc.

Do not skip Phase 1 and try to call `create_host`/`create_client` directly — the convenience methods `host_with_lobby`/`connect_to_lobby` depend on a lobby already existing, and manually managing peer connections without a lobby is much more error-prone (no member enumeration, no reconnect handling, no chat/kick scaffolding to build on later).

## Host flow

```
1. Call Matchmaking.createLobby(LobbyType.LOBBY_TYPE_FRIENDS_ONLY, maxMembers)
   - Use FRIENDS_ONLY for now (not PUBLIC) — no need for public lobby list yet, and
     it avoids test lobbies cluttering searches if app ID 480 (Spacewar test ID) is
     in use during dev.
   - maxMembers: use whatever the current player cap constant is (check TODO.md /
     VERTICAL_SLICE.md — v1 slice targets 2 players, but don't hardcode 2 if a
     constant already exists elsewhere for max players).

2. This is ASYNC. Do not assume success synchronously. Wait for the lobby_created signal.

3. In the lobby_created handler:
   - Check the Result enum parameter equals RESULT_OK
   - If not OK: log the failure reason, show an error to the player, do NOT proceed
   - If OK: store the returned lobby ID in NetworkManager's state (e.g. a
     private/internal field, not necessarily global — check existing NetworkManager
     structure first)

4. A SEPARATE lobby_joined signal will also fire (host auto-joins their own lobby).
   Wait for this too before proceeding — do not proceed on lobby_created alone.

5. In the lobby_joined handler, check the response field equals
   ChatRoomEnterResponse.CHAT_ROOM_ENTER_RESPONSE_SUCCESS.

6. On success: call MultiplayerPeer.host_with_lobby(lobbyId).
   - This internally calls create_host + add_peer for all existing lobby members.
   - Check the returned Error enum — OK means success, anything else is a failure
     to log.

7. Assign the resulting peer object to Godot's Multiplayer.MultiplayerPeer property
   (the standard Godot high-level multiplayer API, so existing/future RPC and
   spawn logic in PlayerSystem works unchanged).

8. NOW the player is hosting. Existing PlayerSystem spawn logic should trigger
   as normal once Multiplayer.MultiplayerPeer is set and Godot's multiplayer
   signals (peer_connected, etc.) start firing.
```

## Client (join) flow

For M1.5, don't build a public lobby browser — rely on Steam's native "Join Game" from the friends list/overlay, which is how real players will actually connect. This means handling TWO entry points:

```
ENTRY POINT A — Friend accepts invite while your game is already running:
1. Friends class emits join_requested(lobbyId, friendId) signal
   (NOTE: this is on the FRIENDS class per GodotSteam docs, not Matchmaking —
   we have not yet fetched the Friends class page; if the signal name or
   signature doesn't match when you check GodotSteam's actual C# API, flag it
   rather than guessing)
2. Handler calls Matchmaking.joinLobby(lobbyId)
3. Proceeds to "Common join completion" below

ENTRY POINT B — Player launches the game via Steam invite/friends-list while
game is NOT running:
1. Steam launches the executable with command-line arg: +connect_lobby <lobby_id>
2. On startup, BEFORE showing MainMenu, check OS.GetCmdlineArgs() (Godot C# API)
   for this pattern
3. If found: parse the lobby ID, call Matchmaking.joinLobby(parsedLobbyId),
   skip the normal MainMenu display and go straight into the join flow
4. Proceeds to "Common join completion" below

COMMON JOIN COMPLETION (both entry points converge here):
5. Wait for the lobby_joined signal (async, same signal host receives, but for
   the client's own join attempt this time)
6. Check response == ChatRoomEnterResponse.CHAT_ROOM_ENTER_RESPONSE_SUCCESS
   - If not success: log the SPECIFIC failure reason (the enum has ~10 distinct
     values — doesn't exist, not allowed, full, banned, community ban, blocked,
     rate limited, etc. — see matchmaking-class.md / main-class.md for the
     full ChatRoomEnterResponse list). Show an error, return to MainMenu.
7. On success: call MultiplayerPeer.connect_to_lobby(lobbyId)
   - This internally finds the host via getLobbyOwner and calls create_client +
     add_peer for all lobby members automatically.
   - Check the returned Error enum.
8. Assign the resulting peer to Multiplayer.MultiplayerPeer.
9. Client is now connected. Existing PlayerSystem logic should spawn/sync as
   normal via Godot's standard multiplayer signals.
```

## For M1.5 testing specifically (before real Steam friends are involved)

Since you'll likely be testing with two Steam accounts you control (or a test partner), the simplest test path is:

1. Host creates lobby, game prints/logs the lobby ID or Steam ID to console/UI
2. Manually communicate that Steam ID to the second tester
3. Second tester's client calls `Matchmaking.joinLobby(lobbyId)` directly — you can wire a temporary debug UI field for entering a lobby ID by hand for testing, rather than relying on the full friend-invite flow initially
4. This lets you validate the MultiplayerPeer plumbing works before wiring up the polished Steam-native invite UX

**Suggestion:** implement the "enter lobby ID manually" test path FIRST (fastest to verify the core transport works), then layer entry points A and B on top once the base connection is proven. Don't try to build all three at once — that's how the scene-file loop happened last time. One working path first, then expand.

## Error handling checklist

Every async Steam call in this flow can fail. For each of these, log the specific error/result code (don't swallow it) and surface something to the player, even if just a debug console message for now:

- `createLobby` → `lobby_created` signal's Result enum
- `joinLobby` → `lobby_joined` signal's `ChatRoomEnterResponse` enum
- `host_with_lobby` → returned Error enum
- `connect_to_lobby` → returned Error enum

## Testing checklist for "done"

- [ ] Host creates a lobby successfully (log confirms `lobby_created` with RESULT_OK)
- [ ] Host's own `lobby_joined` fires with SUCCESS (auto-join confirmed)
- [ ] `host_with_lobby` returns OK, `Multiplayer.MultiplayerPeer` is assigned
- [ ] Second client joins via manual lobby ID entry (test path)
- [ ] Client's `lobby_joined` fires with SUCCESS
- [ ] `connect_to_lobby` returns OK, `Multiplayer.MultiplayerPeer` is assigned on client too
- [ ] Both players see BOTH capsules on screen, movement syncs in both directions
- [ ] Disconnect one client — host doesn't crash, remaining player can continue (basic robustness, not full reconnect handling — that's later)

Once this checklist passes, M1.5 is done. Do not add save/load, combat, or other features in this milestone — those come in M3/M4 per VERTICAL_SLICE.md.
